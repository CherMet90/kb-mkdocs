# Файловые системы Linux

## Основы

### Журнал и «грязная» файловая система

ext4 — журналируемая ФС: перед изменением метаданных она сначала пишет планируемую операцию в отдельный журнал и лишь потом применяет к разделу. Если работу прервать (авария питания, снимок с живой системы), часть транзакций остаётся невыполненной — ФС помечается как «грязная». Это не порча, а нормальное состояние, которое ядро устраняет само.

- Журналируемые ФС (ext4) после аварийного завершения или снятия снимка с работающей системы оставляют невоспроизведённые транзакции в журнале. В суперблоке при этом выставлен признак «журнал требует воспроизведения».
- Журнал воспроизводится автоматически при первом монтировании в режиме rw (и при запуске `e2fsck` без `-n`). До воспроизведения метаданные могут выглядеть повреждёнными, хотя фактически всё в порядке.
- `Filesystem state: clean` говорит лишь о том, что ФС была корректно размонтирована; признак необходимости воспроизведения журнала при этом может оставаться выставленным.
- `Maximum mount count: -1` и `Check interval: 0` означают, что автоматический `fsck` по счётчику монтирований или по интервалу не сработает — «грязный» журнал просто воспроизведётся ядром.

### Что смотреть в суперблоке

Суперблок — главный заголовок ФС: в нём лежат состояние, счётчики монтирований, набор фич и история ошибок. Читается утилитой `dumpe2fs -h <device>`, которая выводит время последнего монтирования и записи, счётчики и признак необходимости воспроизведения журнала.

### Инструменты

Для осмотра и ремонта ext4/FAT служит семейство e2fsprogs и `fsck.vfat`. Главное отличие с точки зрения безопасности — пишет ли инструмент на диск: «читающие» утилиты можно запускать всегда, «пишущие» — только когда правки допустимы.

| Инструмент | Назначение | Пишет на диск |
|---|---|---|
| `dumpe2fs -h` | Суперблок ext4: состояние, времена, фичи, счётчики | нет |
| `e2fsck -fn` | Проверка «на всякий случай»: ответ «нет» на все вопросы | нет |
| `e2fsck -fy` | Ремонт | **да** |
| `debugfs` | Разбор inode и каталогов (`stat`, `ncheck`); запись — только с `-w` | нет |
| `fsck.vfat -n` / `-a` | FAT-разделы, в том числе ESP у UEFI-загрузки | `-n` — нет |
| `blkid`, `lsblk -f` | UUID / PARTUUID / LABEL | нет |
| `mount -o ro,noload` | Просмотр содержимого без воспроизведения журнала | нет |

**Важно:** `e2fsck -n` не даёт полной картины: он не воспроизводит журнал, а на вопросы (например `Salvage?`) отвечает «нет» и аварийно завершается. Реальные ошибки покажет только ремонтный прогон `-fy` — и он меняет диск.

**Ограничение:** `fsck`/`e2fsck` недопустимы по ФС, смонтированной в rw. Проверять «живую» ФС можно только в режиме `-n`, помня о предупреждении выше.

### Разметка дисков с UEFI-загрузкой

Тип раздела определяет, какая на нём ФС и какой утилитой его проверять. Современные серверные и облачные образы используют GPT с несколькими разделами, среди которых есть и ext4 (корень), и FAT (ESP — загрузчик UEFI), требующий отдельного инструмента.

- GPT-разметка современных серверных и облачных образов: корневой раздел + небольшая заглушка `bios_grub` (для GRUB в режиме BIOS, в облачных образах ~4 МиБ) + ESP — FAT-раздел загрузчиков UEFI (обычно 100–600 МиБ, LABEL `UEFI`). Проверяется `fsck.vfat`, а не `e2fsck`.
- `blkid` отдаёт UUID (нужен для `fstab` и параметра `root=UUID=…`) и PARTUUID (нужен загрузчику) — фиксируй их перед переносом диска.

## Кейс: проверка ФС на диске, развёрнутом из снимка

```bash
# состояние ФС: чисто/грязно, будут ли автоматические проверки
dumpe2fs -h /dev/vdb1 | egrep 'Filesystem state|Maximum mount count|Check interval|Last mount|Last write'

# безопасная проверка без правок
e2fsck -fn /dev/vdb1

# что за каталог/inode, на который жалуется e2fsck
debugfs -R "ncheck <inode>" /dev/vdb1
debugfs -R "stat <inode>"  /dev/vdb1

# ESP и идентификаторы разделов
fsck.vfat -n /dev/vdb15
blkid /dev/vdb1 /dev/vdb15

# осмотр содержимого без воспроизведения журнала (диск не меняется)
mount -o ro,noload /dev/vdb1 /mnt && ls /mnt && umount /mnt
```

**Как отличить «журнал» от реальной порчи:** сравни `mtime` элемента из `debugfs -R "stat <inode>"` со значением `Last write time` суперблока. Если правка позже — она ещё в журнале и уйдёт при воспроизведении.

**Важно:** ремонт (`e2fsck -fy`) на эталонной копии делай только тогда, когда её можно пересоздать (например, диск, разворачиваемый из снимка): ремонт переписывает метаданные, и побайтовое состояние для разбора теряется.

**Важно:** у ESP после аварии обычно выставлен только `dirty bit` — снимается при первом монтировании или `fsck.vfat -a`.

**Примечание:** `debugfs` по умолчанию открывает ФС read-only; для записи нужен явный ключ `-w`.
